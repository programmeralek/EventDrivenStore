# Inventory Service — Data Model (As Implemented)

This document describes the **current data model of the Inventory Service** as it exists in the system today.

The Inventory Service is the **system of record for inventory availability and reservation decisions**, including:
- Product stock levels
- Reservation attempts per order item
- Reservation outcomes (success/failure) via emitted events

It does **not** manage orders or payments directly.

---

## Database Overview

- Database name: `inventory_db`
- Engine: Microsoft SQL Server
- Migration tool: EF Core Migrations
- Schema ownership: Inventory Service exclusively

All tables in this schema are **owned and mutated only by the Inventory Service**.

---

## Tables Overview

| Table | Purpose |
|-----|-------|
| `StockItems` | Stores current available quantity per product |
| `StockReservations` | Stores per-item reservation attempts and status |
| `ProcessedEvents` | Idempotency log for consumed `OrderCreated` events |
| `OutboxEvents` | Transactional outbox for inventory domain events |
| `__EFMigrationsHistory` | Tracks applied EF Core migrations |

---

## `StockItems` Table

### Purpose
Represents the **authoritative stock level** for each product.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `ProductId` | Unique product identifier (primary key) |
| `AvailableQuantity` | Current available stock for the product |

### Key Characteristics
- One row per product
- `AvailableQuantity` is the source of truth for reservation checks
- No foreign keys are defined in the current schema

---

## `StockReservations` Table

### Purpose
Stores **reservation attempts** per order item.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `Id` | Reservation row identifier |
| `OrderId` | Owning order identifier |
| `ProductId` | Product reference |
| `Quantity` | Quantity requested |
| `Status` | Reservation lifecycle state (enum) |
| `CreatedAt` | Reservation creation timestamp |

### Reservation Lifecycle (Defined States)
Valid states defined in code include:
- `PENDING`
- `CONFIRMED`
- `REJECTED`
- `RELEASED`

### Key Characteristics
- One row per order item
- Status is stored as an enum-backed integer
- No foreign keys are defined between reservations and stock items

---

## `ProcessedEvents` Table

### Purpose
Implements **consumer-side idempotency** for `OrderCreated` events.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `EventId` | Unique event identifier (primary key) |
| `ProcessedAt` | When the event was handled |

### Why This Exists
- Prevents re-processing when Kafka redelivers
- Ensures reservation logic runs **at most once** per `OrderCreated` event

---

## `OutboxEvents` Table

### Purpose
Implements a **transactional outbox** for inventory domain events.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `Id` | Event row identifier |
| `AggregateType` | Aggregate emitting the event (e.g., `Order`) |
| `AggregateId` | Order identifier |
| `EventType` | Type of inventory domain event |
| `Payload` | Serialized event data |
| `CreatedAt` | Event creation timestamp |

### Why This Exists
- Guarantees atomicity between DB state and event emission
- Prevents lost events on crashes
- Enables reliable retries by a background publisher

Events are inserted in the same transaction as reservation writes and are removed after successful publish.

---

## `__EFMigrationsHistory`

### Purpose
Tracks applied EF Core migrations.

### Characteristics
- **Managed entirely by EF Core**
- Append-only
- Guarantees schema consistency across environments

---

## Why Inventory Emits Events but Owns No Reactions

Inventory consumes one upstream event:
- `OrderCreated`

Inventory emits two downstream events:
- `InventoryReservationSucceeded`
- `InventoryReservationFailed`

It does **not**:
- Create orders
- Process payments
- Perform fulfillment

Those responsibilities belong to other services, keeping Inventory:
- Focused on stock truth
- Deterministic under retries
- Decoupled from order/payment side effects

---

## Summary

The Inventory data model is intentionally:
- Simple
- Inventory-focused
- Event-driven
- Authoritative for stock and reservation outcomes

It acts as the **decision point for inventory availability** while remaining cleanly isolated from downstream concerns.
