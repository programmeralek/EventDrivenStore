# Billing Service — Data Model (As Implemented)

This document describes the **current data model of the Billing Service** as it exists in the system today.

The Billing Service is the **system of record for payment attempts and outcomes**, including:
- Capturing payment results per order
- Publishing payment outcome events
- Persisting pricing snapshots needed for billing decisions

It does **not** manage orders or inventory directly.

---

## Database Overview

- Database name: `billing_db`
- Engine: MariaDB (MySQL-compatible)
- Migration tool: none in-repo (schema provisioned externally)
- Schema ownership: Billing Service exclusively

All tables in this schema are **owned and mutated only by the Billing Service**.

---

## Tables Overview

| Table | Purpose |
|-----|-------|
| `payments` | Stores payment attempts and final status per order |
| `order_pricing_snapshot` | Caches order totals from `OrderCreated` events |
| `processed_events` | Idempotency log for consumed events |
| `outbox_events` | Transactional outbox for payment domain events |

---

## `payments` Table

### Purpose
Represents a **payment attempt and outcome** for an order.

### Structure (As Implemented)

| Column | Description |
|-----|-----------|
| `id` | Auto-increment payment row identifier |
| `order_id` | Order identifier being billed |
| `amount` | Total amount charged |
| `status` | Payment status (`PENDING`, `PAID`, `FAILED`) |
| `created_at` | Creation timestamp (default: `CURRENT_TIMESTAMP`) |

### Key Characteristics
- Written once per billing decision
- Status is decided at the time of reservation success handling
- `status` is stored as a string value (not a DB enum)
- No foreign keys are defined in the current schema

---

## `order_pricing_snapshot` Table

### Purpose
Stores a **pricing snapshot** received from Orders so Billing can act without querying Orders directly.

### Structure (As Implemented)

| Column | Description |
|-----|-----------|
| `order_id` | Order identifier |
| `total_amount` | Total monetary amount from the order event |
| `created_at` | Snapshot creation timestamp (default: `CURRENT_TIMESTAMP`) |

### Key Characteristics
- Populated from `OrderCreated` events
- Inserted with `INSERT IGNORE`, implying **one snapshot per order**

---

## `processed_events` Table

### Purpose
Implements **consumer-side idempotency** for billing decisions.

### Structure (As Implemented)

| Column | Description |
|-----|-----------|
| `event_id` | Unique event identifier (primary key) |
| `processed_at` | When the event was handled (default: `CURRENT_TIMESTAMP`) |

### Why This Exists
- Prevents duplicate billing when Kafka redelivers
- Ensures payment logic runs **at most once** per event

---

## `outbox_events` Table

### Purpose
Implements a **transactional outbox** for payment domain events.

### Structure (As Implemented)

| Column | Description |
|-----|-----------|
| `id` | Event row identifier |
| `aggregate_id` | Order identifier |
| `aggregate_type` | Aggregate emitting the event (e.g., `Order`) |
| `event_type` | Type of payment event (`PaymentSucceeded`, `PaymentFailed`) |
| `payload` | Serialized event data |
| `created_at` | Event creation timestamp |

### Why This Exists
- Guarantees atomicity between DB state and event emission
- Prevents lost events on crashes
- Enables reliable retries by a background publisher
- `payload` is stored as JSON text and validated by a DB check constraint

Events are inserted in the same transaction as payment writes and are removed after successful publish.

---

## Why Billing Emits Events but Owns No Reactions

Billing consumes upstream events:
- `OrderCreated`
- `InventoryReservationSucceeded`

Billing emits downstream events:
- `PaymentSucceeded`
- `PaymentFailed`

It does **not**:
- Create orders
- Reserve inventory
- Perform fulfillment

Those responsibilities belong to other services, keeping Billing:
- Focused on payment outcomes
- Deterministic under retries
- Decoupled from order and inventory side effects

---

## Summary

The Billing data model is intentionally:
- Small
- Event-driven
- Focused on payment outcomes
- Authoritative for billing decisions

It acts as the **payment outcome authority** while remaining cleanly isolated from upstream and downstream concerns.
