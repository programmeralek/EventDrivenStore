# Orders Service — Data Model (As Implemented)

This document describes the **current data model of the Orders Service** as it exists in the system today.

The Orders Service is the **system of record for order intent**, including:
- Order creation
- Item composition
- Pricing snapshot
- Order lifecycle state

It does **not** manage inventory or payments directly.

---

## Database Overview

- Database name: `orders_db`
- Engine: MySQL
- Migration tool: Flyway
- Schema ownership: Orders Service exclusively

All tables in this schema are **owned and mutated only by the Orders Service**.

---

## Tables Overview

| Table | Purpose |
|-----|-------|
| `orders` | Stores order identity, pricing, and lifecycle state |
| `order_items` | Stores immutable item composition per order |
| `pending_events` | Transactional outbox for domain events |
| `flyway_schema_history` | Tracks applied schema migrations |

---

## `orders` Table

### Purpose
Represents a single business order and its lifecycle.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `id` | Unique order identifier |
| `status` | Current lifecycle state of the order |
| `total_amount` | Total monetary value of the order |
| `created_at` | Order creation timestamp |

### Key Characteristics
- `total_amount` is **calculated at creation time**
- `status` is mutated only through domain rules

---

## Order Lifecycle Enforcement

Orders follow a **strict, forward-only lifecycle**, enforced in the domain layer.

Valid states observed today include:
- `CREATED`
- `INVENTORY_REJECTED`
- `INVENTORY_RESERVED`
- `PAID`
- `PAYMENT_FAILED`

Invalid transitions are rejected at runtime by domain guards.

This ensures:
- No state regression
- No resurrection of failed orders
- Deterministic behavior under retries

---

## `order_items` Table

### Purpose
Stores the **immutable composition** of an order.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `id` | Unique item row identifier |
| `order_id` | Owning order |
| `product_id` | Product reference |
| `quantity` | Quantity ordered |
| `price` | Price per unit at order time |

### Key Characteristics
- Items cannot be modified after creation
- Pricing is captured at the time of ordering
- Inventory and Billing do **not** query this table directly

---

## `pending_events` Table

### Purpose
Implements a **transactional outbox** to safely publish domain events.

### Structure (Conceptual)

| Column | Description |
|-----|-----------|
| `id` | Event row identifier |
| `aggregate_type` | Aggregate emitting the event (`Order`) |
| `aggregate_id` | Order identifier |
| `event_type` | Type of domain event |
| `payload` | Serialized event data |
| `created_at` | Event creation timestamp |

### Why This Exists
- Guarantees atomicity between DB state and event emission
- Prevents lost events during crashes
- Enables reliable, repeatable publishing

Events are **inserted in the same transaction** as order state changes.

---

## `flyway_schema_history`

### Purpose
Tracks applied database migrations.

### Characteristics
- **Managed entirely by Flyway**
- Append-only
- Guarantees schema consistency across environments

---

## Why Orders Emits Events but Owns No Reactions

Orders currently emits one event
`OrderCreated`

Orders does **not**:
- Reserve inventory
- Process payments
- Perform fulfillment

Those responsibilities belong to downstream services, keeping Orders:
- Deterministic
- Side-effect free
- Easy to reason about

---

## Summary

The Orders data model is intentionally:
- Simple
- Explicit
- Lifecycle-driven
- Authoritative for business intent

It serves as the **starting point** for the entire event-driven flow, without coupling itself to downstream outcomes.
