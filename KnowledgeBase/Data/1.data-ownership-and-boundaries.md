# Data Ownership and Service Boundaries

This document defines **data ownership, write boundaries, and persistence responsibilities** across the EventDrivenStore system.

The goal is to make **data authority explicit**, prevent accidental coupling, and ensure that the distributed Saga remains correct, observable, and evolvable.

---

## Core Principle: Database per Service

Each domain service owns **exactly one database**.

No service:
- Reads another service’s database
- Writes another service’s database
- Shares tables, schemas, or migrations

All cross-service communication happens **exclusively through events**.

---

## Service-to-Database Ownership Matrix

| Service | Database | Engine | Ownership Scope |
|------|--------|--------|----------------|
| Orders Service | `orders_db` | MySQL | Order lifecycle, pricing, and business intent |
| Inventory Service | `inventory_db` | MSSQL | Stock levels, reservations, availability decisions |
| Billing Service | `billing_db` | MariaDB | Payments, billing decisions, and financial outcomes |

---

## Orders Service Data Ownership

**Authoritative source for:**
- Order identity
- Order status lifecycle
- Item composition
- Pricing intent at order creation time

**Writes:**
- Orders
- Order items
- Order status transitions

**Emits events:**
- `OrderCreated`
- `OrderCancelled` (future)
- `OrderCompleted` (future)

**Never writes:**
- Inventory state
- Payment state

---

## Inventory Service Data Ownership

**Authoritative source for:**
- Product stock
- Reservation decisions
- Stock depletion rules

**Writes:**
- Inventory items
- Stock reservations
- Reservation outcomes

**Consumes events:**
- `OrderCreated`

**Emits events:**
- `InventoryReservationSucceeded`
- `InventoryReservationFailed`

**Never writes:**
- Orders
- Payments

---

## Billing Service Data Ownership

**Authoritative source for:**
- Payment attempts
- Payment outcomes
- Financial state transitions

**Writes:**
- Payment records
- Pricing snapshots (read models)
- Outbox events for payment results

**Consumes events:**
- `OrderCreated`
- `InventoryReservationSucceeded`

**Emits events:**
- `PaymentSucceeded`
- `PaymentFailed`

**Never writes:**
- Orders
- Inventory

---

## Read Models vs Source of Truth

Some services store **derived or duplicated data** intentionally.

Example:
- Billing stores an **order pricing snapshot**
- Orders remains the **source of truth for pricing intent**
- Billing uses the snapshot only to complete its own responsibility

This duplication is:
- Explicit
- Immutable
- One-way
- Event-driven

No service ever queries another service to “reconstruct” state.

---

## Idempotency and Message Safety

Each service enforces idempotency locally using:
- `processed_events` tables
- Event IDs as immutable identifiers

This guarantees:
- Safe replays
- At-least-once delivery tolerance
- No duplicate side effects

---

## What This Architecture Prevents

This design explicitly avoids:
- Shared databases
- Distributed transactions
- Synchronous service-to-service calls
- Hidden coupling through foreign keys or joins
- “Just one quick query” anti-patterns

---

## Why This Matters

Clear data ownership enables:
- Independent deployments
- Horizontal scalability
- Fault isolation
- Safe schema evolution
- Realistic production behavior

Every subsequent data model in this project builds on these rules.
